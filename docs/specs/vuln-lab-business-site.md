# apps/vuln-lab: 自己ペネトレーションテスト用「地域ビジネスサイト」

## Goal

新規ワークスペースアプリ `apps/vuln-lab` として、個人経営の地域ビジネス（カフェ/美容室/学習塾など）
の店舗サイトを作成する。想定は「非エンジニアがAIに具体的なセキュリティ要件を伝えずに丸投げ発注した」
体（てい）の実装で、公開ページ・お問い合わせフォーム・会員ログイン付き予約機能（マイページ）・管理画面
（お知らせ投稿・問い合わせ一覧閲覧）の4機能を、発注文にある範囲を超えずに一通り動かす。このアプリは
ユーザー（将来ホワイトハッカーを目指す本人）が自分自身に対して攻撃練習を行うための「的（まと）」で
あり、曖昧な発注文の自然な実装結果として生まれる典型的な脆弱性（IDOR・SQLi・XSS・認証/セッション
不備・設定不備・暗号化不備・CSRF・設計不備など）を、4機能の範囲内で意図的に温存したまま完成させる
ことがゴールである。`apps/web` や本流の公開ジャーナルとは完全に分離し、デプロイ経路には一切乗せない。

## Non-goals

- 本番運用に耐えるセキュリティ対策を施すこと（このアプリに関してはむしろ逆）。
- 元の発注文にない新機能を、脆弱性カテゴリの置き場所を作るためだけに追加すること。具体的には
  以下の2つは追加しない（Background の「spec レビュー確認事項への回答」参照）。
  - 会員登録・ログインなしで予約内容を照会できる導線。
  - 管理画面のお知らせ投稿における外部リンクのプレビュー取得（サーバー側での任意URL取得）機能。
- 管理画面からのお知らせ削除・編集・ステータス変更などの操作（投稿と閲覧のみに留める）。
- SSRF・脆弱な依存パッケージのカテゴリを成立させること（上記の非追加の結果、この2カテゴリは
  意図的にスコープ外とする。詳細は Background 参照）。
- ランダムなバックドア・遠隔攻撃機能・破壊的機能・他者への攻撃転用が可能な機能（実際のRCE、外部
  ネットワークへの攻撃ツールなど）を仕込むこと。
- 決済処理、実メール送信、多店舗対応、i18n、モバイルアプリなど、地域ビジネスサイトとして本質的でない
  機能。
- `apps/vuln-lab` を CI・Docker・Vercel等いずれの自動デプロイ経路にも接続すること。
- `apps/vuln-lab` に対して自動化されたセキュリティテスト/脆弱性スキャンをリポジトリに組み込むこと
  （攻撃はユーザー本人が手動で行う前提）。
- 一般的なセキュリティレビュー（`/security-review` 等）の指摘に基づいて、このアプリの意図的な脆弱性
  を安易に修正すること。

## Background / context

- モノレポは Turborepo + pnpm workspaces。既存ワークスペースは `apps/web`（Next.js 16 / React 19 /
  Auth.js + Prisma Adapter）と `packages/database`（Prisma 7, PostgreSQL, Auth.js 用スキーマ）のみ。
  `pnpm-workspace.yaml` は `apps/*` と `packages/*` を workspace パッケージとして自動的に拾う。
- ルートの `package.json` スクリプトは Turborepo 経由で「そのタスク用スクリプトを定義している
  workspace パッケージだけ」に対して実行される（`turbo run <task>`）。`check` のみ例外で、
  `biome check .` をリポジトリ直下から直接リポジトリ全体に対して実行する（turbo 経由ではない）。
- `.github/workflows/ci.yml`（GitHub Actions、これが本リポジトリでの唯一の「CI」）は
  `pnpm check → pnpm typecheck → pnpm db:migrate:deploy → pnpm test → pnpm build →
  playwright install → pnpm test:e2e` を素の `pnpm <script>` 呼び出しでルートから実行しており、
  対象パッケージを絞り込むフィルタは今のところ無い。デプロイ先は README の「未決定事項」の通り未確定
  （直近のコミット `docs: mark deploy target as no plan, scaffold only` の通りで、Vercel 設定等は
  リポジトリに存在しない）。デプロイ経路として現状唯一具体的なのは `apps/web/Dockerfile`
  （`DOCKER_BUILD=1` のときだけ Next.js の `output: "standalone"` を有効化する構成）であり、これも
  `apps/web` 専用。
- `packages/database` は Auth.js 用モデル（`User`/`Account`/`Session`/`VerificationToken`）を持つ
  共有 Prisma スキーマで、README にも「将来 web 以外のアプリからも共有」する前提で書かれている。
  本機能はこのアプリを**共有しない**（後述の「完全分離」要件）。
- `/feature` ループの実装検証は `pnpm check/typecheck/test/build`（必要なら `test:e2e`）を実行する
  想定（ルート `CLAUDE.md`）。`/feature-apply` の最終検証も同じコマンド一式を再実行する
  （`RUNBOOK.md` 6-3）。このため `apps/vuln-lab` は最低限 `typecheck`/`test`/lint（Biome）は素直に
  通る状態を保ちつつ、ビルド・E2E・CIには一切乗らない設計にする必要がある（詳細は Requirements 参照）。
- 「意図的に脆弱性を残す」という方針は、ユーザー本人が自己学習目的として既に合意済みの前提である
  （ユーザーの発注文に明記あり）。実装フェーズでは通常のセキュアコーディング最優先の姿勢をこのアプリ
  に限り適用しない。ただしこれは「無差別に酷い実装をする」ことを意味せず、「曖昧な発注文への
  自然な実装として典型的な脆弱性が残る」という制約の中で作る。

### spec レビューの確認事項への回答（本仕様に反映済み）

前回レビューで挙がった2点について、ユーザーから明示的な回答を得ている。以下は本仕様全体に
すでに反映済みの内容であり、実装フェーズで再検討する余地はない。

1. **IDOR/SSRF のために元の4機能にない新機能（ログイン不要の予約照会、管理画面のリンクプレビュー
   取得）を追加してよいか → 追加しない。** 4機能の範囲内に厳密に留める。
   - IDOR は、マイページの「予約詳細ページ」で所有者チェックを省略することで自然に発生させる
     （Requirement 16）。これは「マイページで予約履歴を閲覧できる」という元の発注の自然な実装粒度
     （一覧→詳細という一般的な画面遷移）の範囲内であり、新機能追加ではない。
   - SSRF のように、機能を無理に追加しないと発生させられないカテゴリは、「脆弱な依存パッケージ」と
     同様にスコープ外として扱ってよい（発生しなくてよい）。本仕様はこの2カテゴリを狙わない。
2. **管理画面の「お知らせ削除」機能を含めてよいか → 含めない。** 元の発注通り、お知らせは
   投稿と（公開ページでの表示を含む）閲覧のみに留め、管理画面からの削除・編集操作は持たせない
   （Requirement 18）。問い合わせ一覧も同様に閲覧のみ（Requirement 12）。

### 意図的に「狙わない」脆弱性カテゴリについて

発注文が挙げる脆弱性カテゴリ一覧のうち、以下の2カテゴリは本仕様のどの Requirement でも明示的に
狙わない。

- **脆弱な依存パッケージ**: `apps/vuln-lab` は `apps/web` と同じ Next.js 16 / React 19 系で
  スキャフォールドする前提であり、その時点の最新・非脆弱なバージョンで依存関係を組む想定のため、
  素直に実装すればこのカテゴリは自然には出現しない。
- **SSRF**: 上記「spec レビューの確認事項への回答」の通り、SSRF の自然な置き場所になり得る
  「管理画面でのリンクプレビュー取得」機能を意図的に追加しないと決めたため、このカテゴリは
  成立させない。

発注文の脆弱性カテゴリ一覧は「これらの範囲に収める」という上限（許可リスト）であって「すべてを
必ず作り込む」という必達チェックリストではないため、これはスコープ逸脱ではない。実装者は
この2カテゴリのためだけに、無関係な古いパッケージを固定したり、外部URL取得のような無関係な機能を
無理に追加したりしないこと（Requirement 22 の記録一覧からもこの2カテゴリは欠落して当然である）。

### 分離・デプロイ除外の設計方針（決定事項）

以下は本仕様における確定方針。実装フェーズで再検討する余地はない前提とする。

1. **DB は完全に独立させる。** `apps/vuln-lab` は `@repo/database` に依存せず、PostgreSQL も使わない。
   アプリ内蔵の軽量 SQLite ストア（例: `better-sqlite3` などの同期ドライバ）を `apps/vuln-lab` 配下
   に置き、スキーマ作成・シードもアプリ内で完結させる。DBファイルはgitignore対象のローカルファイル
   （例: `apps/vuln-lab/.data/dev.sqlite3`）とする（Requirement 2・Acceptance criteria 参照）。
   これにより `packages/database`／`apps/web` 側の Postgres には一切触れない。
   `better-sqlite3` のような同期ネイティブドライバを Next 16 / Turbopack 配下で使う場合、ルート
   `CLAUDE.md` に既出の `transpilePackages` の例と同様、`apps/vuln-lab/next.config.ts` に
   `serverExternalPackages: ["better-sqlite3"]`（または採用したドライバの相当設定）が必要になる
   可能性が高い。実装時に解決が必要な既知の詰まりどころとして先に記載しておく（不要と判明すれば
   省いてよい）。
   もう一点、本リポジトリの `pnpm-workspace.yaml` は `allowBuilds`（現状 `@prisma/engines` /
   `@swc/core` / `prisma` のみ許可）でネイティブ/postinstallビルドスクリプトを実行できる依存先を
   allowlist 制御しており、この pnpm バージョンではリスト外の依存パッケージの build スクリプトは
   実行されない。`better-sqlite3` のようなコンパイル済みネイティブバインディングを要するドライバを
   採用する場合、そのパッケージ（または実際にビルドスクリプトを持つ依存先パッケージ）を
   `allowBuilds` に追加しないと `pnpm install` 後にネイティブバインディングが生成されず、
   `pnpm --filter vuln-lab dev` / `test` が失敗しうる。これも `serverExternalPackages` 同様、
   実装時に解決が必要な既知の詰まりどころとして先に記載しておく。ビルドスクリプト不要な純JS
   実装のSQLiteドライバ（例: `sql.js`、Node組み込みの実験的 `node:sqlite`）を選べば、この
   詰まりどころ自体を回避できる（Requirement 2 参照）。
2. **`apps/vuln-lab/package.json` には `build` / `start` / `test:e2e` スクリプトを定義しない。**
   Turborepo は対象スクリプトを持たない workspace パッケージをそのタスクから自動的に除外するため、
   ルートの `pnpm build` / `pnpm start` / `pnpm test:e2e`（および `/feature-apply` の最終検証、CI）
   はこのアプリを一切ビルド・起動・E2Eテストしない。`dev` / `typecheck` / `test`（Vitest 単体テスト）
   は定義する。`lint` は定義してもしなくてもよい（任意）——
   ルートの `pnpm check` は `biome check .` をリポジトリ直下から**直接リポジトリ全体**に対して実行
   する（turbo 経由でも、個々の workspace パッケージの `lint` スクリプト経由でもない）ため、
   `apps/vuln-lab` に `lint` スクリプトが無くても `pnpm check` は `apps/vuln-lab` 配下のコードを
   問題なくチェックする。`dev` / `typecheck` / `test` はビルドでもデプロイでもない、ただのコード
   品質チェックであり、ルートの `pnpm typecheck` / `pnpm test` / `pnpm check` に自然に含まれてよい
   （ローカルの日常検証・`/feature` ループ内検証としては含める。CI については 3. の通り明示的に
   除外する）。
3. **`.github/workflows/ci.yml` は `apps/vuln-lab` に対して一切コマンドを実行しない。**
   `pnpm build` / `pnpm test:e2e` は 2. により自動的に対象外になるが、`pnpm check` /
   `pnpm typecheck` / `pnpm test` のステップは明示的に `apps/vuln-lab` を除外するよう `ci.yml` を
   変更する（例: `pnpm typecheck` / `pnpm test` のステップの turbo 呼び出しに `apps/vuln-lab` を
   除外するフィルタ引数を追加する。`pnpm check` は turbo 経由ではなく `biome check .` を直接呼ぶため、
   `ci.yml` の `pnpm check` ステップ自体を `apps/vuln-lab` を除外した個別の `biome` CLI 呼び出し
   （例: 対象パスの明示指定、または `--ignore`/無視パターンをそのコマンドライン引数として渡す形）
   に置き換える）。**`biome.json` のグローバルな ignore 設定を編集する方法は採らない** ——
   `biome.json` を編集すると、CIだけでなくローカルの `pnpm check` からも `apps/vuln-lab` が除外
   されてしまい、「ローカルの `pnpm check` は `apps/vuln-lab` を含めて通る」という Acceptance
   criteria と矛盾する。除外はあくまで `ci.yml` のそのステップの呼び出し方（CLIレベル）でのみ行う
   こと。結果として GitHub Actions のどのジョブ・ステップログにも `apps/vuln-lab` に対する実行が
   一切現れないこと。
4. **Docker / Vercel 等のデプロイ設定には触れない。** `apps/vuln-lab` 用の `Dockerfile` は作らない。
   `apps/web/Dockerfile` やルートの Docker 手順を変更しない。Vercel 設定はリポジトリに存在しないため
   新規に追加しない。
5. **`turbo.json` はこのままで変更不要**（`tasks` はスクリプト名ベースの一般定義であり、2. の通り
   スクリプトを定義しなければ自動的に対象外になるため）。もし実装上どうしても `turbo.json` に手を
   入れる必要が生じた場合は、「このアプリはデプロイしない」という意図がコメント等で明示的にわかる
   形にすること。
6. **ルートの `pnpm dev`（全アプリ開発起動）に含めるか、`pnpm --filter vuln-lab dev` によるオプトイン
   起動のみに留めるか。** 元の発注文はこの点について何も述べておらず、`pnpm dev` は `apps/web` の
   日常開発で全エンジニアが頻繁に使う既存コマンドである。ここに含めると、`apps/web` の作業のために
   `pnpm dev` を打つだけで、意図的に脆弱性を残したローカルサーバーが毎回自動的に立ち上がるようになる
   （逆に含めなければ `apps/web` 開発者には一切見えないが、`vuln-lab` を触る際は毎回
   `pnpm --filter vuln-lab dev` を明示的に打つ必要がある）。本仕様では利便性を優先し
   **含める** 方針を採用する（ポート衝突を避けるため `apps/web`（デフォルト3000）とは別ポート
   （例: 3100）で起動する）が、これは低リスクかつ`apps/vuln-lab/package.json` の `dev` スクリプトを
   一時的にリネームするだけで即座に元に戻せる可逆な選択であり、「唯一の正解」ではない。ユーザーが
   むしろオプトイン起動のみを望む場合は実装前後どちらでも遠慮なく変更してよい。

## Requirements

### スキャフォールド・分離

1. `apps/vuln-lab` を新規 workspace アプリとして作成する（Next.js 16 / React 19 / App Router /
   TypeScript strict、リポジトリの既存アプリと同じ基本構成に揃える）。`pnpm-workspace.yaml` の
   `apps/*` パターンに自動的に含まれる。`apps/vuln-lab/package.json` の `name` フィールドは、
   `apps/web` の `"name": "web"`（スコープなし）に倣い、`vuln-lab`（スコープなし。
   `@repo/vuln-lab` のようなスコープは付けない）に固定する。以降の Requirements・Acceptance
   criteria が前提とする `pnpm --filter vuln-lab dev/typecheck/test` および `ci.yml` 側の除外
   フィルタは、すべてこのパッケージ名で解決される。
2. `apps/vuln-lab` は `@repo/database` に依存しない。DB接続・スキーマ・マイグレーション・シードは
   すべて `apps/vuln-lab` 内で完結させる（Background の設計方針1参照）。DBファイル（例:
   `apps/vuln-lab/.data/dev.sqlite3`）はリポジトリにコミットしない。ルートまたは
   `apps/vuln-lab/.gitignore` に、このDBファイル（が置かれるディレクトリ、例: `apps/vuln-lab/.data/`）
   を除外パターンとして追加すること。採用するSQLiteドライバがネイティブ/postinstallビルド
   スクリプトを要する場合（例: `better-sqlite3`）、`pnpm-workspace.yaml` の `allowBuilds`
   allowlist（Background 参照）にそのパッケージ（または実際にビルドスクリプトを持つ依存先
   パッケージ）を追加すること。この対応自体を避けたい場合は、ビルドスクリプト不要な純JS実装の
   ドライバ（例: `sql.js`、実験的な `node:sqlite`）を選定してもよい。
3. `apps/vuln-lab/package.json` は `dev` / `typecheck` / `test` スクリプトを定義し、`build` /
   `start` / `test:e2e` は定義しない（Background の設計方針2参照）。`lint` スクリプトの定義は任意
   とする（無くてもよい。ルートの `pnpm check` が `biome check .` をリポジトリ全体に直接実行する
   ため、個別の `lint` スクリプトが無くても Biome によるチェックは行われる）。`dev` はデフォルトの
   3000番とは別ポート（例: 3100）で起動する。
4. `.github/workflows/ci.yml` を変更し、`apps/vuln-lab` に対してどのステップも一切実行しないように
   する（Background の設計方針3参照）。この除外は `ci.yml` の各ステップの呼び出し方（CLI引数・
   フィルタ）レベルでのみ行い、`biome.json` のグローバルな ignore 設定を編集する方法は採らない
   （ローカルの `pnpm check` から `apps/vuln-lab` が除外されてしまうため）。既存の `apps/web` /
   `packages/database` に対する CI の挙動は変更しない。
5. `apps/vuln-lab` 用の `Dockerfile` やその他デプロイ設定ファイルは作成しない。ルートの
   README/RUNBOOK のデプロイ関連記述（Docker手順等）は変更しない。
6. `apps/vuln-lab/CLAUDE.md` を新規作成し、少なくとも次の3点を明記する: (a) このアプリは自己学習用に
   意図的に脆弱性を残したアプリであり、一般的なセキュリティレビューで見つかった問題を安易に修正しては
   ならないこと、(b) 絶対に公開・デプロイしないこと（ローカル/localhost限定）、(c) 意図的な脆弱性の
   カテゴリ一覧（後述の「意図的な脆弱性の記録」参照）へのポインタ。
7. `apps/vuln-lab` 直下に簡潔な README（または既存 CLAUDE.md 内）を用意し、起動方法
   （`pnpm --filter vuln-lab dev` 等）とローカル限定であることを明記する。
8. ルート `README.md` の「ディレクトリ構成」に `apps/vuln-lab` の短いエントリを追加する。
   `apps/web` / `packages/database` と並べて書き、一目でわかるラベル（例:
   「意図的に脆弱性を残した自己ペネトレーションテスト用アプリ・localhost限定・build/CI/デプロイ対象外、
   詳細は `apps/vuln-lab/CLAUDE.md`」）を付す。ルートREADMEしか読まない将来の閲覧者が、この
   アプリの存在と「なぜビルド/CIに出てこないのか」を発見できるようにすることが目的であり、
   スタック表や他セクションまで大改編する必要はない。

### 公開ページ

9. トップページ、サービス紹介ページ、店舗情報ページ（住所・営業時間・アクセスなど）を用意する。
   業種名・店名・具体的なコピーは実装時に決めてよい（個人経営のカフェ/美容室/学習塾のいずれか）。
10. お知らせ一覧ページ（管理画面から投稿したお知らせを公開表示する）を用意する。

### お問い合わせフォーム

11. 公開の問い合わせフォーム（氏名・メールアドレス・本文）を用意し、送信内容をDBに保存する。
12. 管理画面から問い合わせ一覧を閲覧できる（本文の改行など簡単な見た目の整形を行ってよい）。
    問い合わせに対して管理画面から行える操作は閲覧のみとし、編集・削除・ステータス変更などの
    操作は持たせない。

### 会員登録・ログイン・予約

13. メールアドレス+パスワードによる会員登録・ログインを用意する（このアプリ専用の認証機構。
    `apps/web` の Auth.js とは独立でよい／共有しない）。
14. ログイン中の会員が予約（希望日時・メニュー/サービス種別・人数などその業態に自然な項目）を作成
    できる。
15. マイページで、ログイン中の会員が自分の予約履歴を一覧閲覧できる。
16. マイページの予約一覧から、個々の予約の詳細ページ（例: `/mypage/reservations/[id]`）に遷移して
    閲覧できる。予約詳細ページは「ログイン中のユーザー自身の予約かどうか」の所有者チェックを省略した
    素朴な実装（ログイン済みであればIDを指定するだけで詳細が閲覧できてしまう、といった実装）で
    構わない。これは「マイページで予約履歴を閲覧できる」という発注の自然な実装粒度（一覧→詳細という
    一般的な画面遷移）であり、新機能追加ではない。会員登録・ログインなしで予約を照会できる導線は
    設けない（Non-goals 参照）。

### 管理画面

17. 管理者ログイン画面を用意する（会員ログインとは別の認証。実装は簡易でよい）。
18. 管理画面からお知らせを新規投稿でき、投稿済みのお知らせを一覧閲覧できる。管理画面からお知らせに
    対して行える操作は投稿と閲覧のみとし、削除・編集・ステータス変更などの操作は持たせない。
    外部リンクの自動取得・プレビュー表示のような、サーバー側でユーザー指定URLを取得する機能は
    持たせない（Non-goals 参照）。

### 実装スタンス（横断的な制約）

19. 会員/管理者のパスワード保存、セッション管理、各画面・APIの認可チェック（Requirement 16 の
    予約詳細ページを含む）、お知らせ・問い合わせ本文の表示、エラー時のレスポンス内容などは、
    「セキュリティ要件を具体的に指定されていない非エンジニアからの発注に対して、AIが素直に・
    実用最優先で実装した結果」として自然に出てくる実装をそのまま採用してよい。バリデーション強化・
    レート制限・CSRFトークン・出力エスケープの追加対応・厳格なパスワードハッシュ化・詳細エラーの
    隠蔽など、通常であれば当然行うべきセキュリティ対策を「わざわざ」実装しないこと。意図的に
    脆弱性を仕込む（textbook的な後付け注入）のではなく、機能要件を最短距離で満たした結果として
    典型的な弱点が残る状態を目指す。
20. 破壊的操作、他者・外部ネットワークへの攻撃に転用可能な機能（実際のコマンド実行、リモート攻撃
    ツール、無差別スキャン機能等）は含めない。

### 意図的な脆弱性の記録

21. `apps/vuln-lab/CLAUDE.md`（または同ディレクトリの README）に、実装の結果として実際に残った
    脆弱性カテゴリの一覧を簡潔に記録する。後でユーザーが攻略ログ/ジャーナルを書く際の参照用であり、
    ユーザー自身が発見する前提のため、具体的な攻略手順（ペイロード例、エンドポイント名、パラメータ名
    など)までは書かない。カテゴリ名と該当機能領域の対応が分かる程度の粒度に留める
    （例:「予約詳細ページまわり: 認可の扱いに注意」といった粒度）。「脆弱な依存パッケージ」と
    「SSRF」は Background に記載の通り本仕様では意図的に狙っていないため、この一覧に登場しなくて
    よい（欠落は想定通りであり、埋め合わせのための作り込みは不要）。

## Acceptance criteria

- [ ] `pnpm install` 後、`pnpm --filter vuln-lab dev`（またはルートの `pnpm dev`）で
      `apps/vuln-lab` がローカル起動し、別ポート（例: `http://localhost:3100`）でアクセスできる。
- [ ] トップ/サービス紹介/店舗情報/お知らせ一覧の各公開ページが表示される。
- [ ] 問い合わせフォームから送信した内容がDBに保存され、管理画面の問い合わせ一覧に（閲覧専用の
      表示として）表示される。
- [ ] 会員登録→ログイン→予約作成→マイページでの予約履歴一覧閲覧→個々の予約の詳細ページ閲覧、
      という一連の操作が動作する。会員登録・ログインなしで予約を照会できる導線は存在しない。
- [ ] 管理者ログイン→お知らせ投稿→管理画面のお知らせ一覧と公開お知らせ一覧ページの両方に
      投稿済みお知らせが表示される。管理画面に、お知らせの削除・編集や外部リンクプレビュー機能は
      存在しない。
- [ ] `apps/vuln-lab` の SQLite DBファイル（例: `apps/vuln-lab/.data/dev.sqlite3`）が `git status` /
      `git check-ignore` で無視対象として扱われる（`.gitignore` にパターンが存在し、`git add -A` を
      しても当該ファイルがステージされない）。
- [ ] ルート `README.md` の「ディレクトリ構成」に `apps/vuln-lab` のエントリが存在し、意図的に
      脆弱性を残した localhost 限定のペネトレーションテスト対象であること、および build/CI/デプロイ
      対象外であることが読み取れる。
- [ ] `pnpm --filter vuln-lab typecheck` と `pnpm --filter vuln-lab test` が通る。
- [ ] ルートの `pnpm check` / `pnpm typecheck` / `pnpm test` が（`apps/vuln-lab` を含めた状態で）
      通る。`biome.json` にはこの目的のための `apps/vuln-lab` 除外設定が存在しない
      （= ローカルの `pnpm check` は `apps/vuln-lab` 配下も対象に含めて実行されている）。
- [ ] ルートの `pnpm build` および `pnpm test:e2e` の実行ログに `apps/vuln-lab`（またはそのパッケージ
      名）に対する処理が一切現れない。
- [ ] GitHub Actions の `ci.yml` を実行した場合、どのジョブ・ステップも `apps/vuln-lab` に対して
      コマンドを実行しない（ワークフロー定義のレビューで確認する）。除外は `ci.yml` 内の各ステップの
      呼び出し（CLI引数・フィルタ）で行われており、`biome.json` の編集によるものではないことを
      レビューで確認する。
- [ ] `apps/vuln-lab` に `Dockerfile` が存在しない。ルートの Docker/README/RUNBOOK のデプロイ関連
      記述に変更がない。
- [ ] `apps/vuln-lab/CLAUDE.md` が存在し、要件6の(a)(b)(c)すべてを含む。
- [ ] 意図的な脆弱性カテゴリの一覧が `apps/vuln-lab/CLAUDE.md`（または README）に記録されている。

## Out of scope / follow-ups

- 実際にユーザー自身が攻撃を行い、発見した脆弱性・修正内容を記録する「攻略ジャーナル」の作成・運用。
- 発見された脆弱性を修正する第2フェーズ（本仕様は「脆弱性を含んだ状態で完成させる」ことがゴールで
  あり、修正は別タスク）。
- 会員登録・ログインなしで予約を照会できる導線、管理画面のお知らせリンクプレビュー機能、お知らせ
  削除機能（いずれも今回のレビューで明示的に対象外と回答された機能。将来これらを追加する場合は
  別途スコープを再検討すること）。
- 決済・実メール送信・SMS通知など外部サービス連携。
- `apps/vuln-lab` 向けの自動セキュリティスキャン・SAST/DASTツールの導入。
- 複数店舗対応、管理者ロールの細分化（今回は単一管理者ロールで十分）。
- Playwright等によるE2Eテストの追加（本アプリはCI/自動テスト網羅の対象外のため見送り）。
